## 3. 已改但未验证的东西（最高优先级）

**放置的支撑面碰撞豁免**，`plan_shelf_transfer.cpp` 的 `attach_held_bottle` 阶段。

**问题**：`fence_shelf_bottom` 是厚 507 mm 的禁入盒，而瓶子被抓住后挂在 TCP 下方约 171 mm，
所以**从悬停点开始瓶底就在盒子里**。原本「允许瓶子接触支撑面」的豁免排在接近段之后，
悬停和整个插入全程都在被它拒绝，报 `eef in collision: bottle - fence_shelf_bottom`。

**改法与一个必须记住的坑**：第一次尝试是把豁免插在 Connect 之后，结果**两边同时 0 解、
没有任何阶段报失败**。原因是 `target_preplace_ik` 是**生成器**——它读的是
`setMonitoredStage()` 指定的那个场景，不是前一阶段的。把它指向 Connect 下游，
就变成 Connect 等生成器出状态、生成器等 Connect 的场景，**互相死等**。
最终改法是把豁免放到 `attach_held_bottle`（Connect 之前）。已编译，**没跑过**。

## 8. 会浪费时间的坑（当天真的踩过）

1. **`tcp_pose_moveit` 这个字段名会骗人。** 示教文件里它**不是** `platform_base_link`
   下的位姿，而是机械臂自身 FK 的结果（与升降高度无关）。
   `/compute_fk` 实测：同一组关节角在升降 0.647 与 0.250 下，
   `r_link7` 在 `platform_base_link` 里的 \(z\) 相差 **0.397 m，正好是升降行程**。
   **凡是跨升降高度比较 TCP 位置的结论，先确认坐标系。**
2. **场景 YAML 里的体素不在 move_group 的规划场景里。** 它们由 MTC 的
   `spawn_scenario_objects` 注入任务内部。要用 `/check_state_validity` 查，
   必须先 `add_voxel_object` + `/apply_planning_scene` 推进实时场景。
3. **`/check_state_validity` 返回的接触点坐标在规划坐标系里**，和场景 YAML 的
   `platform_base_link` 对不上（实测 \(z\) 差近 1 m）。定位物体靠连杆对和穿透深度，别靠这个坐标。
4. **`ros/` 下的入口必须用系统 python 跑**（conda 环境里没有 rclpy），
   而且 `PYTHONPATH` 要**追加**不要覆盖，否则会把 ROS 的路径冲掉。
5. **只读会话（`take_control=False`）不允许读 TCP**，要用 `tcp_from_joints(joints_deg())` 代替。
6. **四元数总角差是个会骗人的姿态指标。** 它把「绕瓶轴的腕部自转」（不同位置本来就必须不同）
   和「瓶子倾斜」（这才是歪）加在一起。要按 `palm_vertical_base` / `finger_axis_base` 分解再看。
