## 2. 三个失败各自的原因

### 2.1 一帧误检，整个层间搜索中止

层间搜索按 `[647, 250]` 逐层找目标。判定逻辑：

```python
if 稳定帧 < 7:
    if 检测命中 == 0:  raise BottleDetectionLost   # "这层没有" → 换下一层
    raise SafetyAbort                              # "故障" → 整个搜索中止
```

分支**只看命中数是不是 0**。当时 P04 根本不在上层，但检测器在上层出了
**1 帧误检**，于是 `1/7` 走进了"故障"分支，搜索**没有继续往下层找**就中止了。

这条设计的初衷是对的（相机坏了不该让升降把每一层跑一遍再怪货架没货），
但阈值放错了位置：**只要检测器有任何误检率，这条就会反复咬人**。
真正的故障信号其实已经单独存在（`CameraFrameUnavailable` 是一帧都没有）。

**状态：已定位，未修。**

### 2.2 两个都叫 "home" 的姿态，相距 228°

这是今天最贵的一个，也是最能说明问题的一个。

profile 里有两个示教位形：

| 名字 | 谁在用 |
|---|---|
| `grasp_start_right_joints_deg`（收拢位） | 整条货架管线，每次抓取的原子门禁都校验它 |
| `home_joints_deg` | 老的 `table_demo` 桌面演示 |

**两者相距 228°。** 侧桌投放这条链路是在 `table_demo` 之上写的，所以它开场
第一件事是"回到 `home_joints_deg`"——而机器人当时正**稳稳地停在收拢位上**。
于是它要横跨 228° 去另一个姿态，结果：

```
路线1: 133 点 → 电子围栏拒绝，TCP 点 141 落在 x=+0.6002
路线2: 规划失败 error=-2
路线3: 134 点 → 电子围栏拒绝，TCP 点 151 落在 x=+0.6024
路线4: 303 点 → 压缩后需 41 条控制指令 > 队列上限 30
安全中止
```

操作者在现场看到的是"两条手臂明明都在 home 位，它却说不在 home 位"。
**这不是机器人的问题，是同一个词指了两个东西。**

**状态：已修。** `home_joints_deg` **从全部三个 profile 里删除了**，
`SafetyProfile` 的字段和加载器也一并删掉——这个旧姿态在项目里不再存在。
全项目现在只有**一个**示教停放位姿：**双臂 grasp_start**
（右臂 + 左臂 + 升降 647，原子门禁每次抓取都整体校验），
右臂那一项通过 `SafetyProfile.taught_rest_joints_deg` 读取。
注意保留的是**双臂那一套**，它是后续要继续用的东西；删的只是旧的单臂 home。

### 2.3 侧桌投放整条链路建在**旧抓取管线**上

修掉 2.2 之后，流程第一次走过起点检查，然后停在"规划到右腕观察位"——
34 个候选依次被淘汰，理由都是"从这个观察位预演后续抓取时够不到"。

**但真正的问题不是这 34 个候选，而是这个阶段根本不该出现。**

从 8-11 三次成功抓取的产物反推（`outputs/runs/20260811_picks/`，
目录里有哪些文件就等于跑过哪些步骤），能用的货架抓取是这 8 步：

```
归位三步（右臂+升降 / 左臂 / 双臂+升降原子门禁）
  → 只规划 MoveIt 栈
  → 夹爪空夹标定
  → capture_mtc_direct_pick_scene   ← 只开固定头部相机，全程不连机械臂
  → apply_demonstrated_grasp_to_scenario  ← 122 个示教点的行模板
  → MTC 规划
  → execute_mtc_trajectory pick
  → normalize_right_arm --skip-lift  收臂
```

`grep -rl "右腕\|观察位\|wrist" pick_p01/*.log` → **零命中**。
**能用的抓取管线里没有右腕相机，也没有观察位。**

而侧桌投放走的是另一条：`run_task.sh` → `run_pick_place_task.py` →
旧 orchestrator 管线（头部粗定位 → **移到右腕观察位** → 右腕精定位 → 抓取）。
那是 table_demo 时代的流程。

**所以 2.2 和 2.3 是同一个根因的两个症状**：
228° 的 home 是旧管线的停放位姿，右腕观察位是旧管线的定位阶段。
两者在新管线里都不存在。

## 3. 为什么"没跑到"比"跑失败了"更值得说

全天四次中止**全部发生在下发运动指令之前**。这不是运气：

- 电子围栏在执行前逐点复核 TCP，越界就拒绝（2.2 的路线 1/3）
- 控制器队列上限在压缩阶段就拒绝（2.2 的路线 4）
- 抓取预演够不到就淘汰候选（2.3）
- 检测不稳就不给坐标（2.1）

代价是进度慢；收益是**一整天没有一次危险动作**，而且每一次中止都留下了
足够定位的证据。今天修掉的两个问题（15° 弦细分、228° 双 home）都是
**靠中止日志定位的**，不是靠猜。
